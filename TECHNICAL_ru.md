# 🛠️ Техническая документация (Minecraft Server Deployment)

Эта документация описывает архитектуру, процесс CI/CD, резервное копирование и скрипты сервера. Для информации об игровом процессе смотрите основной [README_ru.md](README_ru.md).

## 🛠️ Архитектура и CI/CD (Jenkins)

Деплой осуществляется автоматически через **Jenkins** по протоколу SSH. Jenkins копирует необходимые скрипты и конфигурации на целевой сервер и запускает/обновляет контейнеры через `docker-compose`.

### Опции деплоя (Jenkins)
По умолчанию запуск сборки Jenkins обновляет всю инфраструктуру целиком. Это включает в себя:
- Обновление основного сервера Minecraft (`mc`).
- Принудительную пересборку Docker-образа мониторинга `warden-monitor` (для обновления Python-зависимостей из `requirements.txt`) перед его перезапуском.

**Обновление мониторинга без даунтайма (Zero-Downtime):**
Если вам нужно обновить только контейнер `warden-monitor`, не перезагружая при этом сам сервер Minecraft (чтобы не отключать играющих игроков), вы можете поставить галочку `DEPLOY_MONITOR_ONLY` при запуске джобы в Jenkins ("Сборка с параметрами"). Этот режим скопирует только скрипты мониторинга и безопасно перезапустит исключительно его контейнер.

### Сборка и деплой кастомных плагинов (WardenLog)
В репозитории есть исходный код кастомного плагина `WardenLog` (папка `plugins-src`). 
Пайплайн Jenkins (`Jenkinsfile`) автоматически:
1. Собирает плагин с помощью Maven в Docker-контейнере.
2. Пропускает сборку, если версия не менялась.
3. Копирует готовый `.jar` файл в папку `/opt/minecraft/data/plugins/` на боевом сервере.
4. Перед запуском контейнеров Jenkins принудительно создает папку `WardenLog` и устанавливает правильные права доступа, чтобы избежать конфликтов с Docker-демоном (который по умолчанию создает директории от имени `root`).
5. Перед копированием удаляет на сервере старые версии `WardenLog-*.jar`, `HalloumiTrader-*.jar` и `GreatBuildings-*.jar`, чтобы не было дублей (`Ambiguous plugin name`).

Второй кастомный плагин — `HalloumiTrader`, странствующий торговец, который продаёт халуми. Подробности в [plugins-src/HalloumiTrader/README_ru.md](plugins-src/HalloumiTrader/README_ru.md).

Третий — `GreatBuildings` («Великие здания мира»): знаменитые здания в масштабе 1:1, суперадмин строит их командой. Подробности в [plugins-src/GreatBuildings/README_ru.md](plugins-src/GreatBuildings/README_ru.md).

Сборка любого плагина из `plugins-src`: `bash scripts/build-plugin.sh <ИмяПапки>`.

Иконки блюд `HalloumiTrader` берутся из необязательного ресурспака в [resourcepack/](resourcepack/README_ru.md). Java-игроки скачивают пак прямо из этого репозитория (сервер предлагает его через `RESOURCE_PACK` в `docker-compose.yml`). Jenkins копирует Bedrock-пак и сопоставление Geyser в `data/plugins/Geyser-Spigot/`.

## 💾 Сохранность данных

Все игровые данные хранятся на хост-сервере в директории деплоя:
`/opt/minecraft/data`

Это гарантирует, что данные (миры, плагины, настройки) полностью сохраняются:
- При жесткой перезагрузке сервера.
- При повторных деплоях новой конфигурации через Jenkins.

### Автоматические бэкапы и проверка консистентности
Контейнер `mc-backup` (`itzg/mc-backup`) раз в сутки (в 2:00) ставит мир на паузу сохранения по RCON (`save-off` / `save-all flush`) и делает инкрементальный снимок в хранилище **Restic** (`/backups`) с удержанием `--keep-last 7 --keep-daily 7`.

**Как проверить бэкап на консистентность:**
Скрипт `scripts/verify-backup.sh` проверяет последний снапшот потоково (без распаковки на диск):
- `restic check --read-data-subset=10%`, свежесть снапшота и отсутствие резкого падения объёма;
- наличие `rcon-cli save-off` / `save-all` / `save-on` в логах `mc-backup`;
- валидацию `world/level.dat`, всех регионов `*.mca` и чанков, SQLite (`PRAGMA integrity_check`), H2 `.mv.db`, `ops.json`, `GreatBuildings/buildings.txt` и `HalloumiTrader/taverns.txt`.

Запуск вручную (например, полная проверка 100% блоков раз в месяц):
```bash
bash /opt/minecraft/scripts/verify-backup.sh --subset 100%
```
По крону на хосте (`0 4 * * *`) проверка запускается автоматически с `--subset 10%` и пишет отчёт в `/opt/minecraft/data/plugins/WardenLog/backup_verify.json` для `warden-monitor`.

**Как восстановить сервер из бэкапа:**
Запустите интерактивный скрипт на сервере (он поддерживает и `.tar`, и Restic-снапшоты):
```bash
bash /opt/minecraft/scripts/restore-backup.sh
```
Или вручную остановите `mc` и `mc-backup`, переименуйте `data` в `data_old` и восстановите нужный снапшот из `backups/` через `restic restore`.

## 🚀 Как запустить

Всё работает автоматически через пайплайн `minecraft` на вашем Jenkins. Любые изменения в `docker-compose.yml` (например, добавление новых плагинов в `MODRINTH_PROJECTS`) после коммита автоматически применятся на сервере.

### Донастройка нового сервера
Конфиги плагинов лежат в `data/` и создаются самими плагинами при первом старте. Образ itzg не запускает собственные init-скрипты, поэтому их один раз правят вручную скриптом `scripts/first-run-setup.sh`:
1. Разрешает символ точки `.` в никнеймах (нужно для Bedrock-игроков).
2. Разрешает до 4 регистраций с одного IP-адреса (удобно, когда вся семья играет из дома через один Wi-Fi). Число входов с одного IP не ограничено (`maxJoinPerIp: 0`).
3. Включает дневное время (`/time set day`) при регистрации и при каждом входе игрока (AuthMe `commands.yml`).
4. Снижает MTU Geyser до 1300, чтобы у Bedrock-игроков по Wi-Fi не было «ClientDisconnection-41».

**Как использовать:** после первого старта сервера выполните на хосте `bash /opt/minecraft/scripts/first-run-setup.sh`. Скрипт перезапускает сервер. Повторный запуск безопасен.

Команды, которые должны выполняться при каждом старте, задаются в `RCON_CMDS_STARTUP` в `docker-compose.yml` (например, OP и права для суперадмина `papa`).

## 📊 Prometheus Метрики & Webhook (Warden)

Контейнер `warden-monitor` собирает и отдает метрики в формате Prometheus на порту `8000` (`http://<SERVER_IP>:8000/metrics`).

### Webhook API (Оповещения)
На порту `8002` (проброшен из `8001` внутри контейнера) работает скрытый API для отправки глобальных объявлений всем игрокам на сервере.
- **Endpoint:** `http://<SERVER_IP>:8002/alert?msg=Ваше_сообщение`
- **Результат:** Все игроки увидят на экране крупный красный текст "ВНИМАНИЕ" и подзаголовок с вашим сообщением.
Это полезно для автоматических скриптов или предупреждений перед рестартом сервера.

### Доступные метрики:

| Метрика | Тип | Описание | Метки (Labels) |
| --- | --- | --- | --- |
| `minecraft_server_online` | Gauge | Статус сервера (1 = работает, 0 = недоступен) | - |
| `minecraft_player_count` | Gauge | Количество игроков онлайн | - |
| `minecraft_server_ping_ms` | Gauge | Задержка (пинг) до сервера в миллисекундах | - |
| `minecraft_backup_verify_ok` | Gauge | Результат проверки бэкапа (1 = ОК, 0 = ошибка, -1 = нет отчёта) | - |
| `minecraft_backup_last_verify_timestamp` | Gauge | Unix-время последней проверки бэкапа | - |
| `minecraft_backup_snapshot_age_seconds` | Gauge | Возраст последнего снапшота в секундах | - |
| `minecraft_backup_snapshot_size_bytes` | Gauge | Размер последнего снапшота в байтах | - |
| `minecraft_backup_corrupt_chunks` | Gauge | Число битых чанков в проверенном снапшоте | - |
| `minecraft_backup_verify_errors` | Gauge | Количество ошибок последней проверки бэкапа | - |
| `warden_tnt_placed_total` | Counter | Общее количество установленных блоков динамита | `player`, `world`, `x`, `y`, `z`, `time` |
| `warden_tnt_exploded_total` | Counter | Общее количество взрывов динамита | `source`, `world`, `x`, `y`, `z`, `time` |
| `warden_player_joins_total` | Counter | Общее количество входов игроков на сервер | `player`, `time` |
| `warden_player_quits_total` | Counter | Общее количество выходов игроков с сервера | `player`, `time` |
